**modes/report-template.md** — Report format specification (per AUDIT-03, AUDIT-04):

This file defines the exact output format Claude must use when generating audit reports. Structure it as follows:

Section 1 — Report Header Format: Define the report title format ("Relatorio de Auditoria de Seguranca — Rock House"), date, project name, detected stack summary, and overall assessment using the metaphor scale (palha/madeira/pedra/fortaleza).

Section 2 — Severity Definitions: Define each severity level with clear criteria (not subjective). Critico = exploitable without authentication, data breach or full system compromise possible, immediate action required. Alto = exploitable with minimal effort, significant impact to confidentiality/integrity, fix within 24h. Medio = requires specific conditions to exploit, limited impact, fix within 1 week. Baixo = theoretical risk or hardening improvement, minimal impact, fix at convenience.

Section 3 — Individual Finding Format: Define the exact structure for each finding. Use this template:

  Finding number and title line (e.g., "### Finding 001: [titulo descritivo]")
  
  Table with fields: Severidade (Critico/Alto/Medio/Baixo), Vetor (which attack vector category), Arquivo (file:line reference), Descricao (what was found, in plain PT-BR without jargon), Impacto (what an attacker could do), Defesa Atual (what protection currently exists — "Nenhuma" if none), Defesa Recomendada (what should be in place), Sugestao de Fix (concrete code example or configuration change).

Section 4 — Summary Table Format: After all findings, include a summary table grouped by severity showing count per level. Include a "Proximos Passos" section listing the top 3 highest-priority fixes.

Section 5 — Empty Report Format: When no vector modules are loaded or no findings detected, the report should still be generated with the header, a note explaining the status (e.g., "Nenhum modulo de vetor carregado" or "Nenhuma vulnerabilidade encontrada"), and the metaphor assessment.

All text examples in PT-BR. Use clear language accessible to vibe coders who are not security specialists.

**modes/kill-chain.md** — Kill-chain analysis methodology (per AUDIT-02):

This file defines the methodology Claude follows to test whether each defense layer holds independently. Structure it as follows:

Section 1 — What is Kill-Chain Analysis: Brief explanation using the Rock House metaphor. An attacker (lobo) tries to break through defense layers (paredes). Each layer must hold on its own — if the outer wall falls, the inner wall must still stop the attack. This is not presence-checking (does a wall exist?) but resistance-testing (does this wall hold WITHOUT the others?).

Section 2 — The Three-Question Test: For each defense mechanism found, Claude must answer three questions: (1) "Se APENAS esta defesa existisse, o ataque seria bloqueado?" (isolation test), (2) "Se esta defesa FALHAR, qual e a proxima camada que segura?" (fallback test), (3) "Existem pelo menos 2 camadas independentes para este risco?" (depth test). If any critical risk has only one defense layer, it is flagged as single-point-of-failure.

Section 3 — Common Defense Layers by Risk Category: List typical defense layers that Claude should look for, organized by risk type. For authentication: input validation, rate limiting, secure session management, MFA. For data access: RLS/authorization middleware, ownership verification, audit logging. For injection: input sanitization, parameterized queries, CSP headers, output encoding. For secrets: environment variables, gitignore, key rotation mechanism. Each layer is independent — Claude checks if removing one still leaves protection.

Section 4 — Kill-Chain Report Section Format: Define how kill-chain results appear in the audit report. For each critical/alto risk, include a "Analise Kill-Chain" subsection showing: the risk, layers found, isolation test results per layer, verdict (protegido / ponto-unico-de-falha / sem-defesa).

Section 5 — Scoring Defense Depth: palha = 0 layers (sem defesa), madeira = 1 layer (ponto-unico-de-falha), pedra = 2 independent layers (defesa solida), fortaleza = 3+ independent layers (defesa em profundidade). This maps to how each risk contributes to the overall project assessment.

Write all instructional text in English (code language per project constraint) but all example output text in PT-BR (report language per project constraint).

<task type="auto">
  <name>Task 2: Expand modes/audit.md into the full audit engine</name>
  <files>modes/audit.md</files>
  <action>
Replace the current 27-line stub with the complete audit engine instructions. This file is the core algorithm Claude follows when audit mode is triggered. It receives the detected stack from SKILL.md Step 1 and must produce a complete audit report.

Structure the file with these sections:

**Header**: Title "Audit Mode" and one-line purpose: scans existing project code against security attack vectors and generates a severity-graded report in PT-BR.

**Step 1 — Receive Stack Context**: State that this mode receives the detected stack from SKILL.md Step 1. List what information is available: detected frameworks, detected infrastructure, project root path. Instruct Claude to confirm the stack detection with the user before proceeding if anything looks wrong.

**Step 2 — Load Vector Modules**: Instruct Claude to check which vector module files exist in the vectors/ directory. For each file that exists, load it. Use a dynamic discovery approach — list the five expected files (injection.md, auth-access.md, secrets-exposure.md, upload-network.md, supply-chain.md) but instruct Claude to also load any additional .md files found in vectors/ (future-proofing). If NO vector modules exist, skip to Step 6 and generate an empty report noting that no vector modules are available yet. Track which modules were loaded for the report header.

**Step 3 — Load Stack Rules**: Instruct Claude to check which stack rule files exist in stacks/ that match the detected stack. Load matching files. If none exist, proceed without stack-specific rules (use only vector module generic rules). Stack rules augment vector detection with technology-specific patterns.

**Step 4 — Scan Project Code**: This is the core scanning step. For each loaded vector module, instruct Claude to:

  (a) Read the vector module to get its detection rules and patterns.
  (b) Use Grep and Read tools to search project files for patterns described in the vector module.
  (c) For each match, evaluate whether it is a true finding or a false positive. Consider context — a pattern in a test file is different from one in production code. A pattern with mitigating code nearby may not be a finding.
  (d) For true findings, record: the file path and line number, which vector category it belongs to, a plain-language description of what was found, the potential impact, what defense currently exists (if any), what defense is recommended.
  (e) Assign severity using the criteria defined in modes/report-template.md.
  (f) Apply stack-specific rules if loaded — these may upgrade/downgrade severity or add stack-specific fix suggestions.

  Instruct Claude to scan systematically: go through each vector module completely before moving to the next. Do not mix vectors. Keep findings organized by vector category.

  Important: instruct Claude to prioritize scanning files that handle user input, authentication, database queries, API endpoints, and configuration over utility/helper files. Provide a priority order: (1) route handlers and API endpoints, (2) authentication and middleware, (3) database queries and models, (4) configuration files and environment handling, (5) client-side code handling user input, (6) other application code. Skip node_modules, .git, build output, and vendor directories.

**Step 5 — Run Kill-Chain Analysis**: After scanning, instruct Claude to load modes/kill-chain.md and perform kill-chain analysis on every Critico and Alto finding. For each such finding, identify all defense layers that exist for that risk and apply the three-question test. Record the kill-chain results alongside the finding.

**Step 6 — Generate Report**: Instruct Claude to load modes/report-template.md and generate the final report following the defined format. The report must be output directly to the user (not written to a file unless the user asks). Include: report header with project info and stack, all findings organized by vector category (not by file), kill-chain analysis for Critico/Alto findings, summary table with counts per severity, overall assessment using the metaphor scale, and "Proximos Passos" with top 3 priorities.

**Step 7 — Offer Follow-Up**: After presenting the report, offer the user three options: (1) "Quer que eu corrija algum finding?" — Claude can attempt fixes, (2) "Quer um checklist de deploy baseado nestes findings?" — routes to checklist mode, (3) "Quer planejar defesas para uma feature nova?" — routes to preventive mode.

**File Exclusions**: List directories and patterns Claude must skip during scanning: node_modules/, .git/, dist/, build/, .next/, __pycache__/, venv/, .env (read for structure, never output contents), *.min.js, *.map files, package-lock.json, yarn.lock.

**Edge Cases**: Handle these scenarios with specific instructions: (a) Very large projects (50+ files) — scan priority files first, ask user if they want a full scan or focused scan on specific directories, (b) No source code files found — report this clearly, suggest the user check they are in the correct project directory, (c) Mixed stacks — load all relevant vector modules and stack rules, note the multi-stack nature in the report header.

Write all instructional text in English. All example output text and user-facing strings in PT-BR.

The file should be approximately 150-200 lines. It replaces the current stub entirely.
